## 0. Полный цикл из схемы геймдизайнера

Автор передал схему со словами «это гд скинул». Фиксируем её как входные требования к плану, без объявления реализованной или проверенной механикой. Она расширяет предыдущий список UI-правок: теперь в проектировании нужны энергия, ночная работа, результаты-файлы и цикл исправлений.

Вход: меню → выбор уровня (пока «Демо») → начало дня.

| Шаг | Действие и результат по схеме |
|---|---|
| 1. Чат с руководителем | Приходит ТЗ: что за игра, дедлайн, бюджет. Руководитель выдаёт цель. |
| 2. Дэшборд концепта | Игрок размещает блоки: жанр, аудитория, сеттинг, стиль, механики, платформа. Соединяет блоки; связи дают бафы/дебафы. Дэшборд генерирует список задач. |
| 3. Таск-лист | Задачи из концепта получают приоритеты: игрок решает, что важнее. Для задач нужны исполнители. |
| 4. Хедхантер | Игрок нанимает и назначает сотрудников. Параметры кандидата: скорость, качество, возможность работы ночью, цена. |
| 5. Рабочий процесс | Сотрудник берёт задачу, тратит энергию и присылает файл-результат в рабочий чат. |
| 6. Конец дня | В схеме два повода: энергия закончилась или задачи закрыты. В обоих случаях день завершается по кнопке. Ночью некоторые сотрудники могут работать; энергия восстанавливается. Точный порядок работы и восстановления ещё не задан. |
| 7. Сборка игры | Файлы из чатов сотрудников соединяются в игру. Это отдельный шаг игрового процесса. |
| 8. Релиз и оценка | На отзывы влияют бафы/дебафы концепта и характеристики сотрудников. Хорошая оценка – уровень пройден. Плохая – файл отправляется сотруднику на исправление, требуется ещё день. |

Формулировка схемы «Отзывы = сумма бафов + характеристики сотрудников» задаёт источники оценки, но ещё не определяет формулу, веса и порог прохождения.

Основной путь: ТЗ → концепт и связи → задачи и приоритеты → найм и назначение → работа и файлы → конец дня/ночь → сборка → оценка. Ветка доработки: плохая оценка → передать файл сотруднику → ещё день → повторная сборка и оценка. Не заменять эту ветку простой пересборкой неизменённого результата.

## 1. Меню и ввод имени

- [ ] Убрать выбор сложности «Стажёр / Дизайнер / Ведущий».
- [ ] На этом месте выбирать игровые уровни/главы. Пока доступен один пункт «Демо».
- [ ] Не выдавать сложности за игровые уровни; будущие уровни – отдельный контент.
- [ ] Изменить цвет текста в окне выбора имени, обеспечить читаемость заголовка и подписей на зелёной панели. Конкретный цвет ещё не выбран; текст ввода и placeholder отдельно проверить на светлом поле.

## 2. Доска как свободный холст

- [ ] Развернуть нынешний сценарий: элементы слева – источники карточек, а не слоты для приёма карточек с поля.
- [ ] Игрок перетаскивает элемент из левой панели на свободный холст, как в Miro.
- [ ] После размещения внутри карточки на холсте игрок выбирает значение: жанр, сеттинг и другие параметры соответствующего типа.
- [ ] Учесть набор блоков из схемы ГД: жанр, аудитория, сеттинг, стиль, механики, платформа. Соответствие прежним типам «фишка / референс» требует пересмотра, а не автоматического переноса старых шести слотов.
- [ ] Слева показывать типы карточек; текущую «руку» готовых вариантов заменить выбором внутри размещённой карточки.
- [ ] Сначала игрок заполняет все необходимые карточки. Затем сам соединяет их ниточками.
- [ ] Только после создания связи показывать её результат: «сочетается», «конфликт», «неизвестно», «нет связи». До соединения не показывать готовую оценку вместо действия игрока.
- [ ] Нынешнюю постоянную легенду этих статусов заменить контекстным отображением результата у созданной связи.
- [ ] Убрать бриф с доски; задание/бриф находится в чате руководителя.
- [ ] Убрать «Цели по доске» с доски; перенести их в отзыв в конце, где оценивается результат.
- [ ] Полностью убрать действия «Исследовать рынок» и «Спросить команду». Не объединять их в другую кнопку исследования, как предлагал старый план.

Последовательность: тип слева → перетаскивание на холст → выбор значения в карточке → заполнение остальных карточек → ручные ниточки → результат каждой связи.

## 3. Отдельная вкладка «Таск-лист»

- [ ] Добавить отдельную вкладку для списка задач.
- [ ] Генерировать задачи из собранного на дэшборде концепта.
- [ ] Дать игроку расставлять приоритеты задач.
- [ ] Из таск-листа передавать задачу в чат нужному человеку.
- [ ] Связать задачу и переписку, чтобы было понятно, какое поручение передано кому.
- [ ] Согласовать назначение задач с наймом: человек должен быть доступен в команде. Точное поведение для ещё не нанятого исполнителя нужно определить при проектировании.

## 4. Чаты и найм

- [ ] В начале новой игры существует только чат с руководителем.
- [ ] Не показывать заранее пустые чаты остальных персонажей, общий чат и ИИ-помощника.
- [ ] Людей нанимать через отдельное окно хедхантера.
- [ ] У кандидатов показывать скорость, качество, возможность работы ночью и цену.
- [ ] Сотрудник выполняет назначенную задачу с затратой энергии и присылает файл-результат в чат.
- [ ] Файл из чата участвует в сборке; при плохой оценке его можно отправить сотруднику на исправление за ещё один день.
- [ ] После найма сотрудника открывать его рабочий чат; там он получает поручения из таск-листа.
- [ ] В вариантах ответа убрать подписи с необходимым количеством дней и денег.
- [ ] Бриф хранить и показывать в переписке с руководителем.

Удаление цены из кнопок ответа само по себе не означает отмену бюджета, календаря или списаний. Автор этого не просил; где и как показывать затраты вне ответов, надо определить отдельно.

## 6. Что ещё определить перед реализацией

Это открытые детали, а не принятые решения:

- Какой набор карточек обязателен для демо, можно ли создавать несколько карточек одного типа и менять их после соединения.
- Достаточно ли любых ниточек либо требуется конкретный набор связей; как это влияет на готовность питча. Автор задал последовательность, но не точное правило блокировки.
- Какие пары дают четыре статуса, когда статус «неизвестно» может измениться после удаления исследований; как оценивать реальные несовместимости независимо от отображения нитки.
- Схема ГД помещает оценку после сборки на шаг «Релиз и оценка». В этом отзыве показывать перенесённые цели. Формулу, порог хорошей оценки и соотношение с прежними четырьмя осями ещё определить.
- Состав кандидатов, условия и стоимость найма, ограничения команды; увольнение не включено в запрос.
- Источник задач теперь задан: концепт на дэшборде. Определить таблицу генерации, состояния, зависимости, влияние приоритетов, распределение ролей и доставку результатов.
- Энергия принадлежит сотрудникам по схеме расхода; уточнить лимиты, стоимость работы, влияние скорости/качества, остановку задачи и восстановление. Нужна ли отдельная энергия игрока, схема не определяет.
- Как рассчитываются ночная работа и отдых: одновременно ли восстанавливается энергия, что происходит с не умеющими работать ночью и незавершёнными задачами.
- Что возвращает игрока к следующему утру при незакрытых задачах, когда доступна сборка и обязательно ли завершать день перед каждой сборкой. Схема показывает конец дня перед сборкой, но не раскрывает все многодневные переходы.
- Что представляет собой игровой файл, как он связан с задачей/сотрудником/версией, как заменить его при исправлении и сохранить историю. Не считать файл реальным исполняемым билдом без отдельного решения.
- Как выбираются файл и исполнитель для исправления, как обрабатываются повторная плохая оценка, отсутствие энергии и достижение дедлайна. Указанное в схеме «ещё день» согласовать с ночной работой и общим календарём.
- Единые параметры демо вместо выбора сложности; отображение и подтверждение затрат вне кнопок ответов; совместимость старых сохранений.

## 7. Приёмка будущей реализации

1. Новая игра: «Демо» → читаемое окно имени → только чат руководителя с брифом.
2. На доске нет брифа, целей, исследования и вопроса команде. Карточка перетаскивается из левой панели на свободный холст; значение выбирается уже на ней.
3. После заполнения карточек игрок соединяет их сам; подпись статуса появляется у созданной связи.
4. Через отдельное окно хедхантера нанимается сотрудник; появляется его чат.
5. Из отдельного таск-листа поручение передаётся выбранному сотруднику в чат. В вариантах ответа нет цен в днях и деньгах.
6. Концепт генерирует задачи; игрок задаёт приоритеты. Назначенный сотрудник тратит энергию, завершает работу и присылает связанный с ней файл в чат.
7. День завершается по кнопке; ночная работа и восстановление энергии следуют согласованным правилам. Незавершённые задачи не исчезают при смене дня.
8. Сборка использует полученные файлы. В итоговом отзыве видны перенесённые цели и оценка, учитывающая связи концепта и сотрудников. Хорошая оценка завершает уровень.
9. Плохая оценка ведёт к передаче файла сотруднику на исправление, ещё одному дню и повторной сборке/оценке с изменившимся результатом.
10. Сохранение/продолжение восстанавливает размещение и значения карточек, ниточки, нанятых людей, доступные чаты, приоритеты и состояние задач, энергию, день/ночь, файлы и доработку без повторного найма/списаний.

Проверять действиями обычного игрока; новые правила покрыть тестами. Сам факт записи этого плана не означает прохождение этих проверок.
